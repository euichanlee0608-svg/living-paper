# 위협 모델

과장 없이 적습니다. 이 문서의 목적은 마케팅이 아니라, 병원 IT·보안 담당자가
"뚫리는 지점이 어디냐"를 10분 안에 파악하게 하는 것입니다.

## 신뢰 가정

| 구성요소 | 신뢰 수준 | 근거 |
|---|---|---|
| 사용자 기기(브라우저) | 신뢰 | 여기가 뚫리면 어떤 E2E 설계도 무의미 (키 사용이 가능해지므로) |
| 원내 노드 | 신뢰 | 평문을 다루는 유일한 서버. 기관 경계 안, 기관 정책으로 통제 |
| 클라우드 릴레이 | **불신** | 유출·압수·내부자·호스팅 사업자 전부 가정 |
| 네트워크 | 불신 | TLS 위에 봉투 암호화를 겹침 — TLS 종단(릴레이)이 곧 공격자일 수 있으므로 |

## 공격 시나리오별 결과

### 릴레이 전체가 유출/압수된다
**얻는 것:** 기기 공개키 디렉터리, 봉투(암호문), 라우팅 메타데이터.
**못 얻는 것:** 키워드·메모·답변·KB 내용 전부. 복호화 키가 릴레이에 존재하지 않음.
검증: 앱 설정 → 개인정보·보안 → "릴레이가 본 것" → 평문 검색 0건. 테스트로도 고정
(`envelope: relay view exposes no plaintext`).

### 릴레이가 능동적으로 공격한다 (MITM)
- **봉투 변조/재라우팅** → GCM AAD + 서명이 깨져 수신 측에서 즉시 거부 (테스트 3건).
- **공개키 바꿔치기** → 유일하게 치명적인 경로. 완화 3중:
  1. kid가 공개키 해시라 바꿔치기 즉시 kid 불일치,
  2. 릴레이의 동일-kid 재등록 거부(첫 등록 승리),
  3. **대면 안전 번호 확인**(설정 → 개인정보·보안) — 릴레이가 통제할 수 없는 채널로 검증.
  확인 전까지 UI가 "미확인" 경고를 유지하는 이유입니다.
- **메시지 삭제/지연** → 가용성 공격은 막지 못함. 탐지(응답 없음)만 가능. 의도된 범위.

### 메타데이터 분석
릴레이는 **누가, 언제, 몇 바이트, 어느 랩으로** 보냈는지 압니다.
"회의 후 질문이 많은 연구원" 같은 패턴은 원리상 노출됩니다.
숨기려면 믹스넷/패딩 계열의 전혀 다른 시스템이 필요하고, 이 제품의 범위가 아닙니다.
**숨기지 않고 명시합니다.**

### 사용자 기기 탈취/멀웨어
- 개인키는 `non-extractable` — 키 *값* 유출은 WebCrypto API 표면에 존재하지 않음.
- 그러나 잠금 해제된 기기의 공격자는 키를 *사용*할 수 있음(정상 앱 흐름으로 질의).
  → 기기 보안(OS 잠금, 원격 초기화)이 전제. "이 기기에서 모두 삭제"가 로컬 대응.
- 기기 내 미팅 기록·답변은 IndexedDB에 평문. OS 키스토어 없는 웹 환경에서
  추가 암호화는 키를 어디에 두느냐의 문제를 뒤로 미룰 뿐이라 채택하지 않음.
  민감 기록의 수명은 사용자가 통제(삭제 버튼).

### XSS
- 모든 템플릿 보간이 기본 이스케이프(`ui/dom.js`), raw는 명시적 `Html` 타입만.
- 외부 스크립트·CDN 0개 — 서드파티 유입 경로 자체가 없음.
- 성공해도 키 반출은 불가(위 항목). 세션 악용은 가능 → CSP 헤더는 배포 환경에서 추가 권장.

### 원내 노드 침해
평문을 다루는 유일한 서버이므로, 여기가 뚫리면 **그 랩의** 데이터는 노출됩니다.
경계 안 장비의 보안은 기관 인프라 정책의 몫이고, 이 설계는 그 반경을
"클라우드 전체"에서 "랩 서버 한 대"로 줄이는 것입니다. 반경 축소가 목적이지
무적이 목적이 아닙니다.

### 복구 코드 분실 / 전 기기 분실
클라우드는 복호화 수단이 없으므로 **복구 불가가 맞습니다.** 이것은 버그가 아니라
제로널리지의 대가이며, 온보딩에서 복구 키트 보관을 강제하는 이유입니다.
코드 재발급은 가능(기기 보유 시) — 재발급 즉시 이전 코드는 무효.

### 문서 수집 경로

업로드한 파일은 기기 안에서만 파싱됩니다. 서버 사이드 파서가 없다는 것은
**파서 취약점의 폭발 반경이 그 탭 하나**라는 뜻이기도 합니다. 다만 PDF 파서는
직접 구현한 것이므로, 악의적으로 조작된 PDF가 파서를 멈추게 할 수는 있습니다
(브라우저 탭 한 개의 문제이며, 키나 데이터 유출로는 이어지지 않습니다).

청크는 봉인되어 노드에 저장되고 LMK로 다시 암호화됩니다. 즉 **문서 내용은
릴레이에게 질문과 동일한 수준으로 불투명**합니다.

### 초대 경로

초대 QR은 공개 정보만 담습니다(랩 id, 릴레이 주소, 초대자 지문, 만료 시각).
QR이 유출되어도 랩 키는 얻을 수 없습니다 — 키는 참여자의 공개키로 감싸서
전달되기 때문입니다.

다만 **초대를 받은 사람이 곧 랩 구성원이 됩니다.** 초대 코드를 아무에게나
뿌리면 그 사람의 공개키에도 랩 키를 감싸 줄 수 있게 되므로, 초대장은 만료
시간을 두고 대면으로 건네는 것을 전제로 설계했습니다. 참여자 지문을 확인하는
단계가 UI에 남아 있는 이유입니다.

## 알려진 한계 (요약)

1. 메타데이터는 보임 — 위 명시.
2. 수신자 축 forward secrecy 없음: 수신자 장기 ECDH 키가 유출되면 그 키로 래핑된
   과거 봉투는 열림. 봉투별 임시 키(발신 축)만 보장. 키 로테이션이 완화책(로드맵).
3. 데모 모드의 노드는 같은 탭 안에 있음 — 암호화 경로는 실제와 동일하나
   물리적 분리는 당연히 데모에 없음. UI에 "브라우저 내 시뮬레이션"으로 표기.
4. 릴레이 정적 토큰은 가용성 통제일 뿐 기밀성과 무관 — 기밀성은 토큰이 아니라 봉투가 담당.
5. JS의 메모리 스크럽(`fill(0)`)은 best-effort — GC 언어의 한계로 보장 아님.
6. 초대 승인이 수동 검증에 의존 — 초대 코드를 가진 사람의 공개키면 랩 키가 감싸집니다.
   대면 전달과 만료가 전제이며, 자동 승인 정책은 넣지 않았습니다.
7. 직접 구현한 PDF 파서·QR 인코더는 감사 대상 코드를 늘립니다. 그 대신 외부 의존성
   0을 얻었고, QR은 레퍼런스 구현과 전량 대조해 정확성을 고정했습니다.

## 테스트로 고정된 성질

`tests/crypto.test.html` 22건 중 보안 성질 직결 항목:

- 비수신자 개봉 불가 / 수신자 삭제 탐지 / 발신자 위장 탐지
- 암호문 1비트 변조 → 개봉 실패 (GCM)
- 라우팅 메타데이터 변조 → 개봉 실패 (AAD 바인딩)
- 봉투마다 새 IV·새 CEK·새 임시 키 (재사용 = GCM 파국이므로 테스트로 봉인)
- 개인키 export 시도 → 예외 (non-extractable)
- 릴레이 뷰에 평문 부재
- 잘못된 복구 코드 → 실패 닫힘(fail-closed)
