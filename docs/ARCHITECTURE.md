# 아키텍처

## 설계 원칙

1. **평문은 신뢰 경계를 넘지 않는다.** 경계 = 사용자의 기기 + 원내 노드.
2. **클라우드는 배달부다.** 인증, 기기 디렉터리, 암호문 큐잉. 그 이상 아무것도.
3. **주장은 검증 가능해야 한다.** "릴레이는 못 읽는다"를 문장이 아니라
   버튼으로 제공한다(보안 탭 → 릴레이가 본 것 → 평문 검색 0건).

```
┌────────────────────────┐   sealed envelope   ┌──────────────────┐   sealed envelope   ┌────────────────────────┐
│  기기 (브라우저)          │ ──────────────────> │  클라우드 릴레이    │ ──────────────────> │  원내 노드               │
│                        │                     │                  │                     │                        │
│  P-256 신원 (반출불가)    │ <────────────────── │  Workers + KV    │ <────────────────── │  Python + Ollama       │
│  봉인/개봉 · 서명/검증    │   sealed answer     │  큐 · 디렉터리     │   sealed answer     │  복호화 · RAG · 생성     │
│  IndexedDB             │                     │  로그: 메타데이터    │                     │  KB (행별 AES-GCM)      │
└────────────────────────┘                     └──────────────────┘                     └────────────────────────┘
        신뢰함                                       신뢰 안 함                                  신뢰함
```

## 봉인 봉투 (wire format)

콘텐츠가 기기를 떠나는 유일한 형태. `src/crypto/envelope.js` 와
`node/server.py` 가 동일 포맷을 구현합니다.

```jsonc
{
  "v": 1,
  "alg": "ECDH-ES+A256GCMKW",      // 수신자별 키 합의 + 키 래핑
  "enc": "A256GCM",                // 본문 암호화
  "sender": "<kid>",               // 발신 기기 id (공개키 해시 16B)
  "aad": {                         // ── 릴레이가 볼 수 있는 전부 ──
    "labId": "lab_kumc_mfx",       //    라우팅에 필요해 의도적으로 공개
    "jobId": "job_...",            //    요청-응답 상관관계
    "type": "explain-request",     //    explain-request | explain-answer
                                   //    kb-ingest | kb-ingest-ack | lab-key-grant
    "ts": 1755500000000
  },
  "recipients": [{                 // 수신자마다 하나
    "kid": "<recipient kid>",
    "epk": { "kty":"EC","crv":"P-256","x":"…","y":"…" },  // 1회용 임시 공개키
    "iv": "<b64u 12B>",
    "ek": "<b64u>"                 // 이 수신자용으로 래핑된 CEK
  }],
  "iv": "<b64u 12B>",
  "ct": "<b64u>",                  // AES-256-GCM(payload), AAD = canonical(header)
  "sig": "<b64u 64B r‖s>"          // ECDSA-P256(header ‖ iv ‖ ct)
}
```

### 암호학적 선택과 이유

| 선택 | 이유 |
|---|---|
| **ECDH-ES (임시-정적)** | 키 합의에 발신자 장기 키가 참여하지 않음 → 기기 키가 나중에 털려도 과거 트래픽 복호화 불가(수신자 축 forward secrecy는 없음 — 위협 모델 참고). 임시 키는 봉투마다 새로 생성. |
| **HKDF `info` 바인딩** | `LP1\|wrap\|alg\|sender\|recipient\|jobId` — 합의된 키를 목적·양자·작업에 묶음. 다른 맥락으로의 키 재사용/재전송 차단. |
| **헤더를 GCM AAD로** | 릴레이가 `labId`/`jobId`를 바꿔치기하면 복호화 자체가 실패. 라우팅 메타데이터는 보이지만 위조는 불가. |
| **서명은 별도(ECDSA)** | 기밀성(누가 읽나)과 진정성(누가 썼나)의 분리. 수신자 목록까지 서명에 포함되어 수신자 삭제·추가도 탐지. |
| **`non-extractable` 개인키** | WebCrypto가 키 반출 API 자체를 제공하지 않음. XSS가 성공해도 키 *사용*은 가능할지언정 키 *유출*은 불가 — 그래서 세션 하이재킹과 키 탈취가 분리됨. |
| **kid = 공개키 해시** | 디렉터리가 이름을 속여도 키가 바뀌면 kid가 바뀜. 릴레이의 첫-등록-승리 정책과 대면 지문 확인이 그 위에 얹힘. |

## 랩 키와 멤버십

- 랩마다 **LMK(랩 마스터 키, AES-256)** 하나. 원내 KB를 저장 시 암호화.
- 멤버 초대 = LMK를 새 멤버 기기 공개키로 **봉투에 넣어 래핑**(`lab-key-grant`).
  초대장도 일반 봉투이므로 서명 검증을 공짜로 얻음.
- **복구 코드**: Crockford base32 160비트, `XXXX-XXXX-…` 8그룹.
  O/0, I/l/1 혼동을 정규화로 흡수. LMK를 이 코드에서 유도한 키로 봉인해 두면
  클라우드에 보관해도 안전(코드 없이는 randomness 160비트).
  **모든 기기를 잃으면 이 코드가 유일한 복구 수단** — 클라우드는 원리적으로 도울 수 없음.

## 데이터 저장

| 위치 | 내용 | 보호 |
|---|---|---|
| 기기 IndexedDB | 개인키 | `non-extractable` CryptoKey — 이 오리진의 JS조차 값 접근 불가 |
| 기기 IndexedDB | LMK | 자기 기기 공개키로 봉인된 봉투로만 저장 |
| 기기 IndexedDB | 미팅·모먼트·답변 | 평문 (기기 밖으로는 항상 봉인되어 나감 — 한계는 위협 모델 문서에 명시) |
| 릴레이 KV | 봉투 (TTL 7일) | 원리적으로 열람 불가. 드레인 시 삭제 |
| 원내 KB | 용어집·SOP·노트 | 행별 AES-GCM(LMK), row id를 AAD로 사용 |

## 프런트엔드 구조

프레임워크 없음. 이유: 이 제품의 구매 결정자는 병원 IT/보안 담당자이고,
감사 대상 코드가 작을수록 통과가 빠릅니다. 앱 전체 외부 요청 0건(폰트·QR·PDF 파서 포함) —
폐쇄망 설치에서도 동일하게 동작하며, 배포본에서 실측으로 확인했습니다.

디자인은 Linear의 시스템을 차용했습니다(헤어라인 보더, 6/12px 라운딩, 조밀한 패딩,
강조색은 주요 동작에만). 강조색만 이 제품의 sky로 바꿨습니다.

- `ui/dom.js` — 태그드 템플릿(`html`). 모든 보간은 기본 이스케이프, `Html` 인스턴스만 raw 통과.
  뷰별 리스너는 `scope()`로 소유되어 재렌더·재방문에서 누적되지 않음.
- `ui/shell.js` — 해시 라우터. 데스크톱 사이드레일 / 모바일 하단 탭 + safe-area.
- 뷰 5개: 미팅(캡처) · 정리(태깅+파이프라인) · 설명(답변 카드) · 지식(KB 열람) · 보안(검증 도구).

## 문서 수집 (kb-ingest)

파일은 **기기 안에서** 텍스트로 풀리고 잘린 뒤, 조각만 봉인되어 노드로 갑니다.
파싱 서비스도, 서드파티 워커도, CDN도 경유하지 않습니다.

```
파일 선택 → 텍스트 추출 → 청킹 → seal(kb-ingest) → 릴레이 → 노드
                                                              ↓
                                        LMK로 행별 암호화해 KB에 적재
                                                              ↓
                                        seal(kb-ingest-ack) → 기기
```

- **PDF 추출**: `DecompressionStream`으로 FlateDecode 스트림을 풀고 텍스트 연산자
  (`Tj`/`TJ`/`'`/`"`)를 읽습니다. 디지털 생성 PDF를 대상으로 하며, 스캔본이나
  특수 글꼴 인코딩은 **깨진 텍스트를 조용히 넣지 않고 명시적으로 실패**합니다.
  지식베이스의 품질이 곧 답변의 품질이라, 실패를 숨기는 쪽이 더 해롭습니다.
- **청킹**: 빈 줄 → 문장 순으로 쪼개 620자 목표, 90자 겹침. 정의가 그것을
  한정하는 문장과 분리되지 않도록 하는 것이 겹침의 목적입니다.
- **저장**: `node/server.py`가 행마다 AES-GCM(LMK)으로 암호화하고, row id를 AAD로
  써서 행을 다른 id로 옮기면 복호화가 실패하게 합니다.

## 멤버 초대

초대 QR에는 **랩 키가 들어있지 않습니다.** 담기는 것은 어느 랩·어느 릴레이인지와
초대자의 키 지문뿐이며, 랩 키는 참여자의 공개키가 도착한 뒤에 그 키로 감싸(`lab-key-grant`)
전달됩니다. 초대장 자체가 일반 봉투이므로 서명 검증을 그대로 얻습니다.

QR 인코더(`src/ui/components/qr.js`)는 직접 구현했습니다 — 바이트 모드, ECC M,
버전 1–20. npm 대신 직접 쓴 이유는 다른 모든 결정과 같습니다: CDN이 필요한 초대 QR은
정확히 그것이 필요한 방에서 실패합니다. Python `qrcode` 라이브러리와 모듈 단위로
전량 대조 검증했습니다(`tests/qr.verify.html`, 45건).

## 데모 ↔ 실서버 전환

같은 프런트엔드가 두 모드로 동작합니다. 설정 탭에서 릴레이 주소를 넣고 `/health`로
연결을 확인한 뒤 전환하면, `MockRelay`가 `HttpRelay`로 바뀌고 탭 안의 노드
시뮬레이터가 멈춥니다. **와이어 포맷이 인터페이스**이므로 뷰 코드는 한 줄도
바뀌지 않습니다.

전환 화면은 그 대가도 함께 보여줍니다 — 실서버에 붙으면 릴레이가 내용은 못 보지만
누가 언제 몇 바이트를 보냈는지는 기록합니다.

## 확장 지점 (다음 단계)

1. **실생성** — `nodesim.js`의 템플릿을 `node/server.py`의 Ollama 호출로 교체
   (와이어 포맷 변경 없음). 수집 문서 검색은 이미 실제로 동작합니다.
2. **임베딩 검색** — 현재는 토큰 겹침 스코어. 교체 지점은 `kb_search()` 한 곳.
3. **릴레이 스케일** — KV 큐를 랩당 Durable Object로. API 불변.
4. **감사 모드** — 원내 노드의 처리 로그를 랩 관리자에게 서명된 형태로 제공.
5. **키 로테이션** — 수신자 축 forward secrecy 확보 (위협 모델 한계 2번).
